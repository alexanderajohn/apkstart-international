# Pass 18 — Live Android Runtime Readiness & Real-Device Validation

This Pass shifts focus from backup cryptography to whether ApkStart International **actually boots and runs Android apps on Windows**. A green Windows CI alone is not evidence of this.

## Built-in Live Android Readiness

Open the main window beneath **Android Profiles**, and click **Check running Android**. It checks the current running emulator, without starting, connecting, downloading, installing, repairing, wiping or changing anything:

- ApkStart must have started the emulator in the **current app session**; external or unverified emulator adoption is refused.
- The serial is bound to the emulator managed by ApkStart. Authorization comes from `adb devices`, not the misleading `get-state` command.
- `adb emu avd name` must match the current Profile's expected AVD. A mismatched AVD is blocked; if the name cannot be observed, status is **limited**, not verified.
- `sys.boot_completed=1`, `ro.build.version.sdk=34` and `pm path android` must succeed. The guest ABI is reported when available.
- Results have **ready / limited / blocked** states, and display no raw file paths, credentials, installed package names or Android logs.

This feature does not measure FPS, install APKs or verify that snapshots survive a restart. It never reboots the emulator to make a check pass.

## Manual Windows 10/11 validation — disposable environment required

CI does not provision a physical Windows Android runtime, so the **real** test is an explicit, separately runnable command. A tester must use their own test machine and disposable Android Profile.

Prerequisites: a running ApkStart Android emulator; a dedicated `adb.exe` already installed as part of its runtime; an identified serial such as `emulator-5554`; the AVD name from `Android Profiles`; Android 14/API 34; and (for install tests) a legitimately signed and harmless test APK with a known launcher. **The synthetic ZIP/APK generated by CI is not a real signed installable APK.**

PowerShell (replace placeholders with values from the test host):

```powershell
$env:ASI_E2E_ADB_PATH = 'C:\\path\\to\\runtime\\platform-tools\\adb.exe'
$env:ASI_E2E_SERIAL = 'emulator-5554'
$env:ASI_E2E_PROFILE_ID = 'p_0123456789abcdef'
$env:ASI_E2E_AVD_NAME = 'apkstart_p_0123456789abcdef'

npm run test:runtime:live -- --readiness
```

This read-only mode verifies the real boot, AVD identity, API and Android package manager. It requires the operator to declare the profile; the CLI checks live AVD identity but cannot independently prove host process ownership.

If the **disposable** secondary Profile is empty and the tester has reviewed the APK, they can explicitly opt into install and launch. This test refuses to overwrite an installed package, never passes `-g` or `-r`, and never uninstalls or clears existing user data.

```powershell
$env:ASI_E2E_APK_PATH = 'C:\\test\\verified-signed-test-app.apk'
$env:ASI_E2E_PACKAGE = 'com.example.testapp'
$env:ASI_E2E_DISPOSABLE_ACK = 'I_CREATED_DISPOSABLE_PROFILE'
npm run test:runtime:live -- --install-launch
```

Then restart the **same disposable Profile** through ApkStart's normal controlled UI and check persistence (read-only):

```powershell
npm run test:runtime:live -- --verify-existing
```

Next **stop Android and switch to a DIFFERENT disposable Profile** through ApkStart's UI. Update `ASI_E2E_PROFILE_ID` and `ASI_E2E_AVD_NAME` to match; start its Android runtime normally. Ensure the test APK is not installed there:

```powershell
npm run test:runtime:live -- --assert-absent
```

The harness does not itself switch profiles, reboot an Android guest or replace APK data. A reported launcher event does **not** guarantee a long-running stable app: inspect the window, permissions and crashes manually, then record evidence. If an AVD name cannot be queried, the test fails closed rather than installing anything.

## Windows CI and completion gates

`test/runtime-readiness.test.cjs` uses deterministic mocks for authorized/unauthorized/offline ADB, profile mismatch, wrong API, boot pending, package manager unavailability and avoidance of destructive commands. Windows Node 20/22 runs the tests; CI also checks that the optional real-device harness can start in `--help` mode. Existing CI builds the **portable Developer Preview without Android runtime** and performs UI smoke with synthetic fixtures.

Before a stable release, provide actual Windows 10/11 results for: installing and launching signed APKs, Android permissions, restart/persistence, two-profile data isolation, multi-GB backup/restore, cold and quick-boot recovery, antivirus/NTFS file locks, and emulator compatibility across GPU/CPU/Hyper-V configurations. These remain **unverified** until run on real hardware.

This preview is independent from RoutineMiku/ApkStart and must remain on the Draft PR until release-blocking checks pass.

| Isolation | In a different empty secondary Profile run assert-absent; return to the first and run verify-existing with the digest. A transport error fails the check. |
| Windows window lifecycle | Inspect and record app contents on first launch, close and relaunch, fullscreen, minimize and restore. The harness observes a guest PID. Visual correctness requires this separate check. |

```powershell
$env:ASI_E2E_CANARY_SHA256 = (Get-FileHash .\expected-canary.bin -Algorithm SHA256).Hash.ToLowerInvariant()
node scripts/asi/live-runtime-smoke.cjs --verify-existing > cold-boot.json
if ($LASTEXITCODE -ne 0) { throw 'Cold-boot validation failed' }
```
